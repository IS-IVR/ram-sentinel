# תשתית Process Lifecycle Core

## מה נוסף

- `ProcessIdentity`: זהות של מופע תהליך לפי PID וזמן יצירה. PID לבדו אינו מזהה יציב.
- `ProcessLifecycleObservation`: צילום מצב לקריאה בלבד. ערכים שאינם זמינים נשארים null.
- `ProcessRelationshipTracker`: מזהה קשר הורה-ילד רק כאשר שני מופעי התהליך נצפו יחד בשתי דגימות רצופות.

## כללי שמרנות

- קשר שלא נצפה ישירות אינו נוצר בדיעבד.
- תהליך הורה שאינו מופיע באותה דגימה אינו מקושר לפי PID ישן.
- PID כפול באותה דגימה נחשב עמום.
- שימוש חוזר ב-PID יוצר זהות חדשה ואינו ממשיך קשר קודם.
- תהליך הורה חייב להיות קיים לפני תהליך הילד; קשר שבו ההורה נוצר מאוחר יותר מהילד נדחה גם אם אותו PID מופיע בשתי דגימות.
- זמן יצירת תהליך עתידי ביחס לזמן הדגימה נחשב נתון לא תקין.
- דגימה כפולה או ישנה נדחית במלואה: היא אינה מעדכנת את רשימת התהליכים, את ה-CPU או את רמת הביטחון של קשרים.
- פער גדול משתי דקות מאפס את רצף התצפיות.
- שתי תצפיות מעניקות Confidence בינוני; שלוש ומעלה מעניקות Confidence גבוה.
- הקשר אינו הוכחה לכך שתהליך הילד מיותר או שניתן לסגור אותו.

## גבולות הגרסה

שכבת Core נשארת נקייה מתלות ישירה ב-Windows. ה-Provider מחובר למחזור הדגימה הקיים, ו-ProcessInventorySampleProcessor מרכז את עיבוד ה-snapshot: הוא מפיק את שורות רשימת התהליכים, את מדדי ה-CPU להיסטוריית האבחון ואת ראיות הקשרים מאותו אובייקט ואותה חותמת זמן. MainForm מעביר ל-Provider את חותמת הזמן של דגימת RAM/CPU/דיסק. דגימות כפולות או ישנות אינן משנות את בסיס ה-CPU ואינן מקדמות קשרים. ניהול Toolhelp נבדק ב-state machine דטרמיניסטי; ProcessPropertyReader נבדק לקריאה יחידה ולשמירת null במקרה של כשל. נוסף Windows integration test שמפעיל את ה-Provider האמיתי מול התהליך הנוכחי ב-GitHub Actions. CI run #71 עבר עם 62/62 בדיקות Core, בדיקת Windows, פרסום x64 והעלאת ארטיפקט. דגימות כפולות או ישנות נדחות לפני יצירת פלט כלשהו, כך שאינן יכולות להחליף שורות תהליכים חדשות. עדיין נדרשת בדיקת UI בפועל ובדיקת עומס ממושכת במחשב חלש. אין המלצות Lifecycle או פעולות אוטומטיות על תהליכים.
