# מנוע אבחון צווארי בקבוק - RAM Sentinel

## 1. מטרת המנוע

המנוע צריך לענות על שאלה אחת: **מה כרגע מגביל את תגובתיות המחשב, ומה הפעולה הבטוחה ביותר שסביר שתשפר אותה?**

הוא אינו מחשב "ציון מהירות" לפי אחוז RAM, ואינו מריץ ניקוי כללי. כל אבחון מבוסס על מדידות לאורך זמן, הקשר למשימה שהמשתמש מתאר, והצלבה בין מדדים.

## 2. חמש משפחות אבחון

### A. מחסור בזיכרון RAM

**מה מודדים**
- Available Physical Memory ב-MB ובאחוזים.
- Memory Load.
- Commit Charge מול Commit Limit.
- Working Set ו-Private Bytes לפי תהליך.
- \Memory\Page Reads/sec ו-\Memory\Page Inputs/sec, כשמוני Windows זמינים.
- פעילות דיסק בזמן מחסור בזיכרון.

**הסתייגות חשובה:** Hard Page Fault מחייב הבאת נתונים מהדיסק, אך הנתונים יכולים להגיע גם מחלקים של EXE/DLL ומקבצים ממופים, ולא רק מקובץ ההחלפה. לכן Page Reads/sec אינו מדד ישיר ל-Page File I/O ואינו מוכיח לבדו מחסור RAM.

**איך מחליטים**
- שימוש RAM גבוה לבדו אינו ראיה מספקת.
- התראה מתחזקת כאשר Available נשאר נמוך לאורך זמן, ובמקביל Commit גבוה או שיש סימני Paging/Hard Faults.
- כדי לחזק אבחון, נדרשת קורלציה באותן דגימות: לחץ RAM קריטי, Page Reads/sec מתמשך, וזמן תגובת דיסק גבוה יחד עם פעילות או תור.
- ברירת המחדל דורשת לפחות 60 שניות של מדידות מתמשכות, עם לפחות 75% דגימות תואמות וללא פער גדול מ-45 שניות.
- קריאות דף בלי לחץ RAM, או לחץ RAM בלי זמן תגובת דיסק ופעילות מתאימים, לא יעלו את רמת הביטחון של אבחון הזיכרון.
- גם כשנמצאה קורלציה, ההסבר יציין שמדד Page Reads עשוי לכלול קובצי תוכנה וקבצים ממופים ואינו מזהה לבדו את מקור הקריאה.
- תהליך עם Private Bytes גבוה הוא מועמד לבדיקה, לא הוכחה שהוא מיותר.

**המלצות מותרות**
- להציג תהליכים שצורכים הרבה זיכרון.
- להציע סגירה רגילה של תוכנת משתמש, לאחר אישור.
- להציג דרכים להפחית עומס בתוך התוכנה עצמה, אם הן ידועות.
- להציע לבדוק אם נדרשת הרחבת RAM, רק אחרי אימות שהמחשב אכן מוגבל בזיכרון.

**אסור**
- לרוקן Standby List או File Cache.
- להקטין Working Set של תהליכים אחרים.
- להשבית או להקטין Page File.
- לסיים תהליך או שירות באופן כפוי.

### B. מעבד CPU עמוס

**מה מודדים**
- CPU כולל באמצעות הפרשי GetSystemTimes.
- CPU לכל תהליך באמצעות הפרשי TotalProcessorTime / GetProcessTimes.
- זמן מדידה ו-Logical Processor Count.
- בהמשך: Threads מובילים כדי לזהות תוכנה עם Thread יחיד שרווי.

**נרמול**
`CPU% = DeltaProcessCpuTime / (DeltaWallTime × LogicalProcessorCount) × 100`

הצגה זו מנרמלת את צריכת התהליך לקיבולת המלאה של המחשב. יש להבהיר למשתמש שתהליך יכול להעמיס ליבה אחת גם כאשר אחוז ה-CPU הכולל אינו גבוה.

**איך מחליטים**
- לא מסיקים עומס מקפיצה של שנייה אחת.
- מחפשים עומס מתמשך לאורך חלון מדידה של לפחות 20-30 שניות.
- מזהים אם תהליך אחד אחראי לחלק משמעותי מהעומס.
- לא משנים Priority או Affinity באופן אוטומטי.

**המלצות מותרות**
- להציג את התהליך המוביל ואת צריכת ה-CPU שלו.
- להציע לסגור תוכנת משתמש בדרך רגילה.
- להציע לעדכן תוכנה או לבדוק תוסף/משימה שלה.
- לפתוח את Task Manager או Resource Monitor לצורך בדיקה נוספת.

### C. דיסק איטי

**מה מודדים**
- Avg. Disk sec/Read ו-Avg. Disk sec/Write, מוצגים ב-ms.
- Current Disk Queue Length.
- % Disk Time / Active Time.
- קריאה וכתיבה לפי תהליך, אם יתווסף Collector אמין.
- זיהוי כונן מערכת וסוג מדיה, כאשר Windows מספקת מידע אמין.

**איך מחליטים**
- מוני PDH אינם נאספים בקצב גבוה יותר מפעם בשנייה; במצב מגש משתמשים בקצב נמוך יותר.
- Spike קצר אינו נחשב צוואר בקבוק.
- זמנים גבוהים לאורך דקה ומעלה הם אות לבדיקה, אך יש לשלב אותם עם עומס, Queue ופעילות המשתמש.
- ספי Microsoft כגון 25ms לאזהרה ו-50ms לביקורת משמשים נקודת פתיחה בלבד, לא כלל קשיח לכל SSD/HDD.
- Queue Length לבדו אינו מספיק; הוא תלוי בסוג הכונן, מספר הכוננים ועומס העבודה.

**המלצות מותרות**
- להציג איזה כונן איטי ומה המדדים שנמדדו.
- להציג אילו תהליכים מבצעים פעילות דיסק, אם המידע זמין.
- להפנות ל-Optimize Drives של Windows כאשר מתאים.
- להציע בדיקת בריאות כונן בכלי ייעודי של יצרן הכונן/Windows, בלי לכתוב נתונים לכונן.

**אסור**
- להריץ Defrag על כל כונן ללא זיהוי סוגו ומצבו.
- לנקות Cache באופן שגרתי.
- להפעיל סריקת דיסק מלאה ברקע.

### D. עומס תוכנות רקע והפעלה

זה אינו מדד יחיד. מדובר בקבוצת מקורות שיכולים להעמיס CPU, RAM או Disk:
- תוכנות שעולות עם הכניסה ל-Windows.
- תהליכים ללא חלון גלוי שצורכים משאבים באופן מתמשך.
- Updaters, Sync clients ו-Helpers.
- תוכנות שהמשתמש אינו מעוניין שיפעלו תמיד.

**חשוב:** אין להסיק שתהליך מיותר רק משום שאין לו חלון. שירותי נגישות, מנהלי התקנים, תוכנות גיבוי ואבטחה יכולים לפעול ברקע מסיבה טובה.

**Startup Impact**
- רשימת Run keys ו-Startup folders היא Inventory בלבד, ולא מדידת השפעה.
- תווית High/Medium/Low תוצג רק כאשר יש מדידה אמיתית של CPU ו-Disk בזמן אתחול/Logon.
- אם אין מדידה, להציג "לא נמדד" ולא לנחש.
- בהמשך אפשר לשלב Windows Event/ETW boot diagnostics ולמדוד מספר כניסות.

**המלצות מותרות**
- השבתה של פריט HKCU בודד בלבד, לאחר הצגת מקור, Publisher, פקודה וגיבוי מדויק.
- Restore בכל עת.
- פריטים לא מוכרים יישארו ללא המלצה עד שיתקבל מידע נוסף.
- HKLM, Services, Drivers ו-Logon Tasks לא ינוהלו אוטומטית בשלב הראשון.

### E. מחסור בשטח אחסון

**מה מודדים**
- נפח כולל ונפח פנוי בכונן Windows.
- אחוז פנוי.
- בהמשך: נפח זמני/מערכת לפי מקורות Windows רשמיים, רק כאשר יש דרך בטוחה ומדויקת להציגם.

**איך מחליטים**
- שטח פנוי נמוך הוא סיכון לעדכונים, קבצים זמניים ופעולות מערכת; הוא לא בהכרח צוואר בקבוק ישיר.
- ספי אזהרה יהיו תלויים בנפח הכונן ובנפח המוחלט שנשאר.
- יש להציג בנפרד "שטח אחסון נמוך" ו-"הדיסק מאט את העבודה".

**המלצות מותרות**
- פתיחת Storage Settings / Storage Sense.
- הצגת קטגוריות ניקוי ש-Windows מציעה.
- הצגת כוננים ומקום פנוי.

**אסור**
- למחוק Downloads, מסמכים, תמונות, נתוני דפדפן או קבצים אישיים.
- למחוק Restore Points, קובצי Update או Cache בלי פירוט, Preview ואישור ברור.

## 3. צינור אבחון אחיד

1. **איסוף:** Collectors קוראים מדדים בלבד.
2. **ניקוי נתונים:** סילוק ערכים חסרים, נתונים לא תקינים ודגימות כפולות.
3. **חלון זמן:** צבירת דגימות כדי להבחין בין Spike לעומס מתמשך.
4. **סיווג:** כל Detector מחזיר Finding או "אין מספיק ראיות".
5. **קורלציה:** חיבור בין RAM, CPU ו-Disk. למשל, RAM נמוך יחד עם Disk latency ו-Hard Faults תומך יותר באבחון Paging מאשר RAM גבוה לבדו.
6. **דירוג ביטחון:** High / Medium / Low לפי מספר מקורות הראיה, משך המצב ואיכות הנתונים.
7. **המלצה:** פעולה אחת או שתיים בלבד, עם תועלת צפויה, סיכון, והפיכות.
8. **אישור:** אין שינוי מערכת אוטומטי ללא אישור משתמש.
9. **אימות:** Before/After באותו workload.

## 4. מבנה Finding

כל Finding צריך להכיל:
- Category: RAM / CPU / Disk / Startup / Storage.
- Status: Healthy / Watch / Action recommended.
- Confidence: High / Medium / Low.
- Title: משפט פשוט בעברית.
- Summary: מה קורה.
- Evidence: מדדים, ערכים, משך זמן ומועד הדגימה.
- Impact: Startup / פתיחת תוכנות / ריבוי משימות / עבודה שוטפת.
- Recommendation: פעולה ממוקדת.
- Risk: Low / Medium / High.
- Reversible: Yes/No.
- RestorePlan: דרך ביטול מפורשת.

## 5. דירוג המלצות

אין "ציון מהירות" שרירותי. סדר ההמלצות נקבע לפי:
1. חומרת ההשפעה שנמדדה.
2. רמת הביטחון באבחון.
3. הסיכוי לשיפור במשימה שהמשתמש ציין.
4. סיכון הפעולה.
5. האם ניתן לבטל אותה.

הצג לכל היותר המלצה ראשית אחת ועוד שתי המלצות משניות. עומס של 15 אזהרות יוצר בלבול במקום שיפור.

## 6. תדירות איסוף

| מצב | RAM / CPU כללי | תהליכים | Disk PDH | Startup |
|---|---:|---:|---:|---|
| Tray רגיל | 30-60 שניות | 30-60 שניות | 30 שניות | לא נאסף |
| חלון פתוח | 5-10 שניות | 10-30 שניות | 5-10 שניות | רק בעת פתיחת הדף/רענון |
| Quick Diagnosis | 1-5 שניות לפי API | 1-5 שניות | לא יותר מפעם בשנייה | סריקה חד-פעמית |
| Extended Diagnosis | לפי תהליך האבחון | לפי הצורך | עד 1Hz | מדידות אתחול ייעודיות |

Windows Performance Counters אינם מיועדים לאיסוף מהיר יותר מפעם בשנייה. לנתונים תכופים יותר יש להשתמש ב-API ישיר מתאים ולא לבצע PDH polling אגרסיבי.

## 7. איכות נתונים ותנאי כשל

- כל Collector יכול להחזיר NotAvailable בלי להפיל את האפליקציה.
- אין להציג 0 כאשר המדד אינו זמין.
- יש לציין מתי המדידה האחרונה בוצעה.
- אם אין מספיק דגימות, התוצאה היא "אוספים נתונים" או "לא ניתן לקבוע".
- מחשב במצב סוללה, חסכון בחשמל, עדכון Windows או סריקת אנטי-וירוס עשוי להראות תוצאה זמנית; יש להציג הקשר כשניתן.
- לא להציג אבחון תרמי ללא חיישן אמין.

## 8. אימות שיפור

לכל פעולה:
1. למדוד Baseline.
2. לבצע שינוי אחד בלבד.
3. לאתחל/להמתין לפי סוג השינוי.
4. לחזור על אותה פעולה לפחות שלוש פעמים.
5. לדווח Median לפני ואחרי.
6. אם אין שיפור מעבר לרעש המדידה, להציג "לא נמצא שיפור מדיד".

מדדים:
- זמן כניסה ל-Idle אחרי Logon.
- זמן פתיחת תוכנה (Cold ו-Warm בנפרד).
- CPU Idle.
- Disk latency בזמן אותו workload.
- Available RAM / Commit / Hard Faults בזמן ריבוי משימות.
- צריכת המשאבים של RAM Sentinel עצמה.

## 8.1 מימוש מדדי Page Reads

ה-Collector קורא את מוני PDH הבאים בקצב מדגם האבחון (30 שניות):
- \Memory\Page Reads/sec - מספר פעולות הקריאה שנדרשו לפתרון Hard Page Faults.
- \Memory\Page Inputs/sec - מספר הדפים שהובאו מהדיסק.

שני המונים דורשים דגימת בסיס לפני חישוב קצב. אם המונה אינו זמין או שהערך אינו תקין, הוא נשאר null ואינו מומר לאפס. אין לבצע המתנה או polling תכוף כדי להשיג את הדגימה הראשונה.

העלאת Confidence ל-High מתבצעת רק כאשר לחץ RAM קריטי, Page Reads/sec מעל הסף, זמן תגובת דיסק של לפחות 25ms ופעילות דיסק של לפחות 50% או תור של 0.5 ומעלה מתקיימים יחד לאורך 60 שניות לפחות. זהו כלל פתיחה שמרני לכיול, לא סף אוניברסלי.

## 9. אבטחה ופרטיות

- כל המדידות מקומיות.
- אין Telemetry או Upload.
- ActionPlan נשמר מקומית לפני ביצוע פעולה.
- כל שינוי מתועד עם Old Value / New Value / Restore.
- אין שינוי שירותי אבטחה, עדכונים, Page File או הגנות מערכת.


## 10. מימוש Core ראשון

מנוע האבחון הראשוני נמצא בקובץ src/RamSentinel.Core/DiagnosticsEngine.cs. הוא מקבל היסטוריית דגימות ומחזיר DiagnosticReport עם ממצאים, ראיות, רמת ביטחון, משך, המלצה, סיכון ותוכנית שחזור. הוא אינו מפעיל פעולות Windows.

בשלב זה ממומשים:

- לחץ RAM מתמשך לפי RAM זמין, Memory Load ו-Commit.
- עומס CPU מתמשך, כולל שיוך זהיר לתהליך מוביל כאשר קיימות מספיק דגימות תהליך.
- זמן תגובת דיסק גבוה לאורך זמן, בתנאי שיש גם פעילות או תור שמחזקים את הממצא.
- מחסור בשטח בכונן Windows, בנפרד מאבחון מהירות הדיסק ובהתחשב גם בנפח המוחלט וגם באחוז הפנוי.
- התעלמות מ-Spikes, ערכים לא תקינים ופערי דגימה גדולים.
- הצגת Startup כ-"לא נמדד" עד שתתווסף מדידת Logon אמיתית.

מגבלות חשובות:

- עדיין לא נאספים Hard Faults / Page Reads, לכן המנוע אינו קובע שהתרחש Paging ואינו מציג זאת כעובדה.
- זיהוי CPU הוא ברמת תהליך; זיהוי Thread מוביל עדיין לא ממומש.
- החיבור הראשוני לממשק והיסטוריית הדגימות המוגבלת מתוארים בסעיף 11. המדידות נשמרות בזיכרון בלבד ואינן שורדות סגירה של התוכנה.
- ספי האבחון הם נקודת פתיחה שמרנית. יש לכייל אותם בבדיקות אמיתיות על מחשבי HDD ו-SSD חלשים, ולא להציגם כאמת אוניברסלית.
- גם ממצא מסוג ActionRecommended הוא המלצה בלבד. מנוע האבחון אינו משנה הגדרות, אינו סוגר תהליכים ואינו מוחק קבצים.


## 11. חיבור חי לממשק - שלב ראשון

- MainForm מוסיף דגימת אבחון כל 30 שניות.
- בזמן שהחלון פתוח, מדדי RAM ו-PDH מתרעננים כל 10 שניות; באזור ההתראות הם מתרעננים כל 30 שניות. היסטוריית האבחון נשארת בקצב של 30 שניות כדי לא להגדיל עומס או להעצים בטעות דגימות צפופות.
- מדידת CPU ורשימת תהליכים נאספות יחד עם דגימת האבחון. תהליך יזוהה כמקור לעומס רק כאשר קיימות מספיק דגימות רציפות וזהות התהליך (PID וזמן יצירה) נשארת יציבה.
- היסטוריה נשמרת בזיכרון בלבד: 30 דקות ועד 61 דגימות. היא אינה נכתבת לקובץ ונעלמת כשהתוכנה נסגרת.
- מסך האבחון מציג ממצא ראשי אחד, עד שני ממצאים נוספים, ראיות מרכזיות והמלצה בשפה פשוטה.
- התוכנה נפתחת בחלון גלוי; המשתמש יכול להעביר אותה לאזור ההתראות בעצמו.
- אין כפתור "האץ עכשיו" שמפעיל ניקוי או שינויים. בשלב זה המערכת מודדת וממליצה בלבד.

מגבלות של השלב הנוכחי:

- היסטוריית מדידות אינה נשמרת בין הפעלות. נדרש זמן איסוף מחדש לאחר הפעלת התוכנה.
- תדירות איסוף ושימוש במשאבי RAM Sentinel עצמה עדיין צריכים בדיקת soak על מחשב חלש.
- אין עדיין זיהוי Paging על סמך Hard Faults, השפעת Startup אמיתית, או קורלציה מלאה בין שלושת צווארי הבקבוק.
- המלצות אינן מבוצעות אוטומטית. כל פעולה עתידית תיבנה כשלב נפרד עם אישור ושחזור.
